## 02｜課題への共感 — 約35秒

**サブタイトル:** こんな経験、ありませんか？

### スライドに載せる

| 左 | 右 |
| --- | --- |
| **日本語を打ちたいのに…** `# konnichiwa`（英語入力のまま） | **英語を打ちたいのに…** `こんｓｔ`（日本語入力のまま） |

下部:

- **そのたびに、消して、切り替えて、打ち直す。**
- （小さく）**「まあ、そういうものだ」——その不便は、いつの間にか当たり前になっている。**

### 伝えたいこと

切り替え忘れは1回は小さくても、繰り返すと作業の妨げになる。しかも多くの人は、それを **仕方ないこととして受け入れている**。

### カンペ

> 例えば、チャットで日本語を入力しようとしたのに、英語のまま『konnichiwa』と入力してしまった。
> 反対に、コードを書こうとしたら日本語入力になっていて、意図しない文字が入力されてしまった。
> 皆さんも、こうした経験はないでしょうか。
> そのたびに文字を消し、入力ソースを切り替え、もう一度入力する。
> 一回は小さな手間ですが、何度も繰り返すと意外とストレスになります。
> それでも私たちは、「入力ソースは自分で切り替えるもの」だと当たり前のように受け入れてきました。

**→ 次:** 「では、なぜアプリごとに言語を切り替えるだけでは足りないのでしょうか？」

## 03｜課題の本質 — 約40秒

**サブタイトル:** 同じアプリでも、入力したい言語は違う。

※ 旧「原因」と旧「理想の体験」を **1枚に統合**

### スライドに載せる

**上段（例: Cursor）**

| チャット欄 | コードエディタ |
| --- | --- |
| 日本語 | 英語 |

**下段**

| 従来 | 理想 |
| --- | --- |
| 入力欄を選択 → 言語を確認 → **手動切り替え** | 入力欄を選択 → **そのまま入力** |

下部（短文）: **その「仕方ない」を、壊したい。**

### 伝えたいこと

本質は **入力欄単位**で言語が違うこと。やりたいのは切替ではなく **書くこと**。手動切替を前提にした当たり前を、壊す必要がある。

### カンペ

> 例えば、私が普段使っているCursorでは、AIとのチャットは日本語で入力します。一方、コードエディタでは英語を使います。
> つまり、同じアプリの中でも、入力する場所によって必要な言語が違います。
> そのため、アプリ単位で入力ソースを固定するだけでは十分ではありません。
> そもそも、私たちが本当にやりたいのは入力ソースの切り替えではなく、文章やコードを書くことです。
> そこで、入力欄を選んだ時点で適切な言語になっていて、そのまま入力できる体験を理想としました。
> 手動で切り替えることを前提にした、その当たり前を壊したい——それが ReadyType の出発点です。

**→ 次:** 「この理想を実現するために開発したのが、ReadyTypeです。」

## 04｜解決策 — 約35秒

**サブタイトル:** 入力欄にフォーカスするだけで、自動切り替え。

### スライドに載せる

- **実画面スクショ** または [デモ動画](https://youtu.be/dPCCXdxS-bg)
- チャット欄 → 日本語 / コードエディタ → 英語
- 下部: **一度ルールを登録すれば、あとは入力欄を選ぶだけ。**

### 伝えたいこと

入力欄ごとのルールに従い **自動切替** する、動く **macOS アプリ**。

### カンペ

> ReadyTypeは、入力欄にフォーカスするだけで、登録したルールに応じて入力ソースを自動で切り替えるデスクトップアプリです。
> 例えば、チャット欄では日本語、コードエディタでは英語に切り替わります。
> 一度ルールを登録すれば、次回からは入力欄を選ぶだけです。
> 現在はmacOSで実装しており、私自身も普段の作業で使用しています。

**→ 次:** 「ルールを設定できても、設定自体が面倒では使い続けられません。」

## 05｜UXの工夫 — 約45秒

**サブタイトル:** 設定も管理も、できるだけシンプルに。

### スライドに載せる（3要素）

| # | 見出し | 内容 | ビジュアル |
| --- | --- | --- | --- |
| 01 | **アプリ・ルール一覧で管理** | アプリを選び、入力欄ごとのルールを確認・編集 | アプリ一覧 ＋ ルール一覧（実画面） |
| 02 | **ショートカットで登録** | 対象入力欄から Quick Set を起動 | `⌥ ⌘ L` ＋ Quick Set（実画面） |
| 03 | **オンボーディング** | 初回に権限・設定を案内 | **文字のみ**（画像なし） |

### 伝えたいこと

自動切替だけでなく **設定・管理・初回体験** まで含めて使いやすく。

### カンペ

> ReadyTypeでは、入力欄ごとのルールを簡単に設定・管理できるよう、UXにもこだわりました。
> まず、アプリ一覧から対象アプリを選び、そのアプリの入力欄ごとのルールを確認・編集できます。
> また、設定したい入力欄で Option・Command・L を押すと、Quick Setが開きます。入力欄の情報をもとに条件候補が提示されるため、複雑な識別情報を自分で調べずに登録できます。
> さらに、初めて利用する方が必要な権限設定などをスムーズに進められるよう、オンボーディングも用意しています。

**→ 次:** 「使い心地にこだわったのには、理由があります。」

## 07｜技術スタック — 約40秒

**サブタイトル:** ReadyTypeを支える技術構成

### スライドに載せる

**採用技術（役割別）**

| 領域 | 採用技術 |
| --- | --- |
| デスクトップ基盤 | Tauri 2 |
| UI | React / TypeScript |
| スタイリング | Panda CSS |
| ルーティング | TanStack Router |
| バックエンド | Rust |
| 開発環境 | mise / Lefthook |
| OS連携 | macOS Accessibility API / TIS |

**構成図（中央）**

```text
React + TypeScript     →  UI・設定画面
Tauri 2 + Rust         →  ルール判定・OS連携
macOS API              →  入力欄の検知・入力ソース切替
```

**採用理由（短文3つ）:** クロスプラットフォーム / リッチなUI / 高速・堅牢

**注釈:** 現在は **macOS のみ**。Windows・Linux は順次対応予定。

### 伝えたいこと

UI と OS 連携を **分離** し、他 OS 展開も見据えた選定。

### カンペ

> ReadyTypeは、Tauri 2を基盤として開発しています。
> フロントエンドにはReactとTypeScriptを採用し、スタイリングにはPanda CSS、ルーティングにはTanStack Routerを使用しています。
> 一方、入力欄の検知や入力ソースの切り替えなど、OSと密接に関わる処理はRust側で実装しています。macOSではAccessibility APIやTISを利用しています。
> また、miseによる開発ツールの管理や、Lefthookによるチェックの自動化も取り入れています。
> Tauriを選んだ理由は、ReactでUIを構築しながら、RustでOS連携を実装でき、将来的な他OSへの展開も見据えられるためです。

**→ 次:** 「技術を組み合わせるだけで、入力欄ごとの切り替えが実現できるわけではありませんでした。」

## 08｜技術的なチャレンジ — 約55秒

**サブタイトル:** 「入力欄の識別」と「確実な切り替え」に挑んだ。

※ 技術スタックの再掲・macOS注釈は **このページでは不要**

### スライドに載せる（左右2領域）

| 01 入力欄の識別 | 02 確実な切り替え |
| --- | --- |
| 共通の安定IDがない | API成功でも実入力に反映されない |
| Accessibility から複数属性を取得 | Electron製アプリなどで発生 |
| 条件を構成しルールと照合 | 再選択・遅延再試行・古い処理の無効化 |

### 伝えたいこと

難所は API 呼び出しではなく、**識別** と **実入力への反映**。

### カンペ

> 技術的に特に難しかったのは、2つあります。
> **1つ目は入力欄の識別です。** macOSには、あらゆるアプリで共通して使える安定した入力欄IDがありません。そこで、Accessibility APIからRoleやIdentifier、DOM関連の属性などを取得し、複数の情報を組み合わせて入力欄を識別し、登録したルールと照合しています。
> **2つ目は、入力ソースを実際の入力欄へ確実に反映することです。** 特にElectron製アプリでは、OSのAPIが成功していても、入力欄では以前の入力ソースが使われ続けるケースがありました。そこで、同じ入力ソースの再選択や遅延再試行を実装しました。また、入力欄が変わったときには古い処理が影響しないよう制御しています。
> こうした問題への対応を重ねることで、実際に使える体験へ近づけてきました。

**→ 次:** 「より多くの人に使ってもらうために、まだ改善したいことがあります。」
