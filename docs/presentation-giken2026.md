## 02｜課題への共感 — 約35秒

**サブタイトル:** こんな経験、ありませんか？

### スライドに載せる

| 左 | 右 |
| --- | --- |
| **日本語を打ちたいのに…** `# konnichiwa`（英語入力のまま） | **英語を打ちたいのに…** `こんｓｔ`（日本語入力のまま） |

下部:

- **そのたびに、消して、切り替えて、打ち直す。**
- （小さく）**「まあ、そういうものだ」——その不便は、いつの間にか当たり前になっている。**

### 伝えたいこと

切り替え忘れは1回は小さくても、繰り返すと作業の妨げになる。しかも多くの人は、それを **仕方ないこととして受け入れている**。

### カンペ

> 例えば、チャットで日本語を入力しようとしたのに、英語のまま『konnichiwa』と入力してしまった。
> 反対に、コードを書こうとしたら日本語入力になっていて、意図しない文字が入力されてしまった。
> 皆さんも、こうした経験はないでしょうか。
> そのたびに文字を消し、入力ソースを切り替え、もう一度入力する。
> 一回は小さな手間ですが、何度も繰り返すと意外とストレスになります。
> それでも私たちは、「入力ソースは自分で切り替えるもの」だと当たり前のように受け入れてきました。

**→ 次:** 「では、なぜアプリごとに言語を切り替えるだけでは足りないのでしょうか？」

## 03｜課題の本質 — 約40秒

**サブタイトル:** 同じアプリでも、入力したい言語は違う。

※ 旧「原因」と旧「理想の体験」を **1枚に統合**

### スライドに載せる

**上段（例: Cursor）**

| チャット欄 | コードエディタ |
| --- | --- |
| 日本語 | 英語 |

**下段**

| 従来 | 理想 |
| --- | --- |
| 入力欄を選択 → 言語を確認 → **手動切り替え** | 入力欄を選択 → **そのまま入力** |

下部（短文）: **その「仕方ない」を、壊したい。**

### 伝えたいこと

本質は **入力欄単位**で言語が違うこと。やりたいのは切替ではなく **書くこと**。手動切替を前提にした当たり前を、壊す必要がある。

### カンペ

> 例えば、私が普段使っているCursorでは、AIとのチャットは日本語で入力します。一方、コードエディタでは英語を使います。
> つまり、同じアプリの中でも、入力する場所によって必要な言語が違います。
> そのため、アプリ単位で入力ソースを固定するだけでは十分ではありません。
> そもそも、私たちが本当にやりたいのは入力ソースの切り替えではなく、文章やコードを書くことです。
> そこで、入力欄を選んだ時点で適切な言語になっていて、そのまま入力できる体験を理想としました。
> 手動で切り替えることを前提にした、その当たり前を壊したい——それが ReadyType の出発点です。

**→ 次:** 「この理想を実現するために開発したのが、ReadyTypeです。」

## 05｜デモ — 約1分

**目的:** オンボーディングから初回設定、入力欄ごとの自動切り替えまでを実画面で見せ、ReadyTypeの使い方と価値を具体的に伝える。

**見せ方:** ライブ実演。画面共有では操作対象を拡大し、操作のたびに「今どこを見ているか」「何が起きたか」を短く説明する。実演が難しい場合は[デモ動画](https://youtu.be/dPCCXdxS-bg)に切り替える。

### 実演の流れ

| 順 | 画面・操作 | 説明 |
| --- | --- | --- |
| 1 | ReadyTypeのオンボーディングを表示 | 初回起動時に、利用に必要な権限や設定を案内する。 |
| 2 | オンボーディングを進め、ReadyTypeのアプリ画面を開く | セットアップ後は、アプリごとのルールを一覧・編集する画面が中心になる。 |
| 3 | **アプリごとの設定画面**を表示 | アプリ単位で入力欄のルールを管理できることを説明する。ここをデモの中心として見せる。 |
| 4 | アクセシビリティ画面を表示 | 入力欄を識別するために必要なアクセシビリティ設定を確認できる。 |
| 5 | 一般画面を表示 | 一般設定を確認できることを一言で紹介する。 |
| 6 | アプリについて画面を表示 | アプリ情報を確認できることを一言で紹介する。 |
| 7 | アプリ画面の赤い閉じるボタンを押す | ウィンドウを閉じてもReadyTypeは終了せず、バックグラウンドで動作し続けることを伝える。Dockにアプリアイコンが表示されないことも見せる。 |
| 8 | Cursorを開き、Terminal欄にフォーカスして `⌥ ⌘ L` を押す | Quick Setを起動し、この入力欄の切り替え言語として英語を登録する。 |
| 9 | CursorのAIチャット欄にフォーカス | **この欄は切り替え言語を事前に登録済み。** フォーカスすると設定した言語に切り替わることを見せる。 |
| 10 | Cursorでファイルを作成し、エディタにフォーカス | **この欄も切り替え言語を事前に登録済み。** AIチャット欄とは別の言語に切り替わることを見せる。 |

### 実演中のカンペ

> まず初回起動時のオンボーディングです。利用に必要な設定を案内します。
> 続いてReadyTypeの画面です。中心となるのはアプリごとの設定画面で、アプリ内の入力欄ごとにルールを管理します。
> こちらはアクセシビリティの設定画面です。一般設定とアプリについての画面も用意しています。
> この赤いボタンで画面を閉じても、ReadyTypeはバックグラウンドで動作を続けます。Dockにもアプリアイコンは表示されません。ここからは、裏側で動いているReadyTypeの動作をCursorでお見せします。
> 次にCursorで、まだルールを登録していないTerminal欄を使ってみます。Option・Command・LでQuick Setを開き、この欄では英語を使うルールを登録します。
> AIチャット欄と、これから作るファイルのエディタ欄は、切り替え言語を事前に登録してあります。それぞれにフォーカスすると、入力欄に合わせて言語が切り替わります。
> このように、アプリ単位ではなく、同じアプリの中でも入力欄ごとに切り替えられます。

**デモの注釈:** アプリ画面を赤い閉じるボタンで閉じた後もバックグラウンド動作が続き、Dockに表示されないことをCursorの実演前に短く説明する。Terminal欄のみ、その場でショートカットから英語を登録する。AIチャット欄とファイル作成後のエディタ欄は、切り替え言語を事前に登録済みであることを画面上で明示する。

**→ 次:** 「このように、設定したルールを日常の入力欄で使えるよう、設定や管理の体験も工夫しています。」

## 08｜技術スタック — 約40秒

**サブタイトル:** ReadyTypeを支える技術構成

### スライドに載せる

**構成図（中央）**

```text
React + TypeScript     →  UI・設定画面
Tauri 2 + Rust         →  ルール判定・OS連携
macOS API              →  入力欄の検知・入力ソース切替
```

**技術選定の経緯:** Flutterで試作 → 切り替え速度とOS連携を重視し、Tauri + Rustへ

**注釈:** 現在は **macOS のみ**。Windows 版は順次対応予定。

### 伝えたいこと

クロスプラットフォームを見据えてFlutterで試作した後、切り替えの応答性とOS連携を重視してTauri + Rustを選んだ。

### カンペ

> ReadyTypeは、Tauri 2を基盤として開発しています。
> 最初のPoCでは、クロスプラットフォームで作れるFlutterを使いました。その後、入力欄に合わせた切り替えの応答性とOS連携をより重視する方針にし、UIとRustのバックエンドを組み合わせられるTauriを採用しました。
> ReactとTypeScriptで設定画面を作り、入力欄の検知や入力ソースの切り替えなど、OSと密接に関わる処理はRust側で実装しています。macOSではAccessibility APIやTISを利用しています。
> ReadyTypeで優先したい応答性とOS連携に合わせて技術を選定しました。現在対応しているのはmacOSです。

## 09｜技術的なチャレンジ — 約55秒

**サブタイトル:** 「入力欄の識別」と「速く、確実に反映すること」に挑んだ。

※ 技術スタックの再掲・macOS注釈は **このページでは不要**

### スライドに載せる（左右2領域）

| 01 入力欄の識別 | 02 応答性と確実な反映 |
| --- | --- |
| 共通の安定IDがない | API成功でも実入力に反映されない |
| Accessibility から複数属性を取得 | Electron製アプリなどで発生 |
| 条件を構成しルールと照合 | フォーカス通知・重複抑止・ロック外でOS連携 |
|  | 反映のための再選択・遅延再選択 |

### 伝えたいこと

難所は API 呼び出しではなく、**入力欄の識別**と、**応答性を保ちながら実入力へ確実に反映すること**。

### カンペ

> 技術的に特に難しかったのは、2つあります。
> **1つ目は入力欄の識別です。** macOSには、あらゆるアプリで共通して使える安定した入力欄IDがありません。そこで、Accessibility APIからRoleやIdentifier、DOM関連の属性などを取得し、複数の情報を組み合わせて入力欄を識別し、登録したルールと照合しています。
> **2つ目は、応答性を保ちながら、切り替えを実際の入力欄へ反映することです。** フォーカス変化はAccessibilityの通知で受け取り、同じフォーカスの重複評価を抑えます。ルール判定の後は状態ロックを解放してからOSの切り替え処理を行い、OS連携の待ちが他の状態処理を塞がないようにしています。
> 一方、特にElectron製アプリでは、OSのAPIが成功しても入力欄では以前の入力ソースが使われ続けることがありました。そこで同じ入力ソースの再選択や、40・120・250ミリ秒後の遅延再選択を行い、入力欄への反映を安定させています。
> フォーカスの重複評価を抑え、OS連携の待ちが他の処理を塞がないようにしながら、実際の入力欄へ反映する工夫を重ねています。

**→ 次:** 「このアプリを知り、使い始められる場所として、ランディングページも用意しています。」

## 10｜LPの構成 — 約25秒

**サブタイトル:** プロダクトを知り、試せる場所も自分でつくる。

### スライドに載せる

```text
Astro（SSG） → 静的HTML・アセット → Amazon S3 → Amazon CloudFront → 利用者
```

- Astroでページを静的生成（SSG）
- 生成したHTML・アセットをS3に配置し、CloudFront経由で配信
- LPからアプリの情報やダウンロード先へ案内

### 伝えたいこと

アプリ本体だけでなく、知ってもらい、利用を始めてもらうためのLPも構築・公開している。

### カンペ

> ReadyTypeを知って、使い始めてもらうためのランディングページも用意しています。
> AstroでHTMLを静的生成し、生成物をAmazon S3に配置、CloudFront経由で配信する構成です。ページを事前に生成しておくことで、シンプルな静的サイトとして公開しています。

**→ 次:** 「公開を入口に、さらに使いやすくするための開発も続けていきます。」

## 12｜結論 — 約30秒

**サブタイトル:** 「あったらいいな」を、「なくてはならない」へ。

### スライドに載せる

**中央（大きく）**

- **第一号のユーザーは、私自身。**
- **あったらいいな、から作った。**
- **なくてはならない、ずっと使い続けたいアプリへ。**
- **自分が使い続けたいから、育てていく。**
- （アクセント）**入力ソース未切替の不便——その当たり前を、壊す。**

**3つの流れ（短文）**

| あったらいいな | 使い続けるうちに | 誰かの日常にも |
| --- | --- | --- |
| 自分の不便から開発 | なくてはならない存在へ | 価値を届け、育てていく |

**フッター:** ロゴ ＋ **ReadyType** — 入力する場所に、適切な言語を。

### 伝えたいこと

自分の課題から始まり、**使い続けるから改善し、届けたい**。そして「仕方ない」とされてきた不便の **当たり前を壊す**。
（技育／IT 業界を支える皆さんへの呼びかけは **07 で本編**、ここでは短く回収。）

### カンペ

> ReadyTypeは、私の日常にあった「あったらいいな」から生まれました。
> 実際に使い続けるうちに、入力ソースを切り替えることを意識せず作業できるようになり、今では自分にとってなくてはならないアプリになっています。
> だからこそ、これからもずっと使い続けたいと思えるように、自分で使いながら改善を続けていきます。
> 利益を目的にするのではなく、自分が使い続けたいものを、同じ課題を持つ皆さんにも本気で届けたい。技育展にいる、コードと日本語を行き来する皆さんに、まず使ってみてほしいと思っています。
> 「あったらいいな」から始まり、「なくてはならない」へ。そして、ずっと使い続けたいアプリへ。
> 入力ソースの切り替え忘れによる不便を当たり前にしないため、ReadyTypeを育てていきます。
> 『入力する場所に、適切な言語を。』
