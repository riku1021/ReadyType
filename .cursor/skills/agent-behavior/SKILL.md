# Agent 行動指針

LLM コーディングの典型的な失敗を減らす行動指針。由来は [Andrej Karpathy の観察](https://x.com/karpathy/status/2015883857489522876)。プロジェクト固有のワークフローと制約は `.cursor/rules/global.mdc` を優先する。常時適用のルール版は `.cursor/rules/shared/agent-behavior.mdc`。

**Tradeoff:** 慎重さ（caution）を速度より優先する。typo 修正など trivial な作業では判断して簡略化する。

出典: [multica-ai/andrej-karpathy-skills](https://github.com/multica-ai/andrej-karpathy-skills)

## 1. Think Before Coding

**前提を黙って決めない。混乱を隠さない。トレードオフを出す。**

実装前に:

- 前提を明示する。不確かなら質問する
- 解釈が複数あるなら提示する。黙って 1 つ選ばない
- より単純な方法があるなら言い、必要なら反論する
- 不明なら止まる。何が不明かを名指しして聞く

## 2. Simplicity First

**問題を解く最小のコード。投機的なものは書かない。**

- 依頼されていない機能を足さない
- 1 回しか使わない抽象化を作らない
- 依頼されていない「柔軟性」「設定項目」を足さない
- 起き得ないシナリオのエラー処理を書かない
- 200 行書けて 50 行で済むなら書き直す

判断基準: シニアエンジニアが「過剰」と言うか。Yes なら単純化する。

## 3. Surgical Changes

**必要な箇所だけ触る。片付けるのは自分の変更で生じた残骸だけ。**

既存コードを編集するとき:

- 隣接コード・コメント・フォーマットを「改善」しない
- 壊れていないものをリファクタしない
- 既存スタイルに合わせる（自分の好みで変えない）
- 無関係なデッドコードに気づいたら言及する。削除しない

自分の変更で orphan が出たとき:

- 自分の変更で未使用になった import / 変数 / 関数は削除する
- もともとあったデッドコードは依頼されない限り削除しない

判断基準: 変更した各行がユーザーの依頼に直接つながるか。

## 4. Goal-Driven Execution

**成功条件を定義し、検証できるまでループする。**

曖昧な指示を検証可能な目標に変換する:

- 「バリデーションを追加」→ 不正入力のテストを書いて通す
- 「バグを直す」→ 再現テストを書いて通す
- 「X をリファクタ」→ 前後でテストが通ることを確認する

多段タスクは短い計画にする:

```text
1. [手順] → verify: [確認]
2. [手順] → verify: [確認]
3. [手順] → verify: [確認]
```

強い成功条件があれば独立してループできる。弱い条件（「動くようにする」）は確認が増える。
